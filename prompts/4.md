## 10. GITHUB WORKFLOW — CREATE BRANCH, COMMIT, PULL REQUEST & AUTO-MERGE TO MAIN

After successfully generating and validating the blog article, you MUST create a GitHub Pull Request containing the new article and then merge it into the `main` branch.

This is a mandatory part of every successful scheduled execution.

### A. REPOSITORY INSPECTION

1. Identify the RailsDev.io GitHub repository.
2. Inspect the repository structure.
3. Identify the blog content directory.
4. Inspect existing article formats and frontmatter conventions.
5. Confirm the `main` branch exists (it is the merge target).
6. Check recent commits and existing pull requests.
7. Ensure the selected article does not already exist.

Never assume repository paths or branch names without inspecting the repository.

### B. CREATE A DEDICATED BRANCH

Create a new branch for each article.

Branch naming convention:

`content/add-article-article-slug`

Example:

`content/add-article-ruby-on-rails-ai-agents`

Requirements:

- Create the branch from the latest `main`.
- Never commit or push directly to main or master.
- Use a descriptive branch name.
- Avoid modifying unrelated files.

### C. CREATE ARTICLE FILES

Generate and add:

1. Complete Markdown article.
2. SEO metadata and frontmatter.
3. Relevant article tags and categories.
4. Featured image references or image metadata, following existing project conventions.

Follow the existing RailsDev.io content architecture.

Do not introduce a new content format unless necessary.

### D. VALIDATE CHANGES

Before committing, verify:

- Markdown syntax.
- Frontmatter validity.
- Article slug uniqueness.
- Code block formatting.
- Internal links.
- External reference links.
- SEO metadata completeness.
- No duplicate content.
- Only intended article-related files are changed.

Run relevant content validation or build checks if repository tooling supports them.

If validation fails, fix the problems before proceeding. If they cannot be fixed, do NOT merge (see G).

### E. COMMIT CHANGES

Use this commit message convention:

`content: add [article title]`

Example:

`content: add building AI agents with Ruby on Rails`

Commit only the files related to the new article.

### F. PUSH BRANCH AND CREATE PULL REQUEST

Push the new branch to the GitHub remote repository.

Create a Pull Request targeting `main`.

PR title convention:

`[Blog] Article Title`

Example:

`[Blog] Building AI Agents with Ruby on Rails`

PR description must include:

##### Article Summary

Brief explanation of the article and its key points.

##### Article Information

- Article title.
- Category.
- Primary keyword.
- Secondary keywords.
- Article slug.
- Content file path.
- Word count.

##### SEO Information

- Meta title.
- Meta description.
- Target search intent.
- Internal linking suggestions.

##### Research References

List important official documentation, GitHub repositories, and research sources used.

##### Validation Checklist

- [ ] Article content reviewed.
- [ ] Technical accuracy checked.
- [ ] Code examples reviewed.
- [ ] SEO metadata verified.
- [ ] Markdown validated.
- [ ] Internal links checked.
- [ ] No unrelated files modified.

### G. AUTO-MERGE THE PULL REQUEST INTO `main`

After the Pull Request is created and verified, merge it into `main` automatically.

Merge ONLY when ALL of these are true:

1. All validation and build checks for the new article passed in this run.
2. The PR targets `main`, has no merge conflicts, and its diff contains only the intended article-related files.
3. Required CI status checks on the PR have completed successfully. Wait for pending checks to finish (poll at reasonable intervals, up to about 15 minutes). If the repository has no required checks, proceed.

How to merge:

- Use a squash merge (or the only merge method the repository allows) with the available GitHub tooling, e.g. `gh pr merge <PR_NUMBER> --squash --delete-branch`.
- Use the PR title as the squash commit title.
- Delete the article branch after a successful merge.

After merging, verify:

- The PR state is MERGED.
- Record the merge commit SHA.
- The article file exists on `main`.

Never:

- Bypass branch protection or required reviews (no `--admin` or equivalent override).
- Merge with failing checks, unresolved conflicts, or unrelated files in the diff.
- Push or force-push directly to `main`.

If the merge is blocked (required reviews, failing checks, conflicts, missing permissions) or times out, leave the PR open, do not retry with overrides, and report the exact reason as a partial success.

Do not run any manual deployment. Any deployment triggered automatically by the merge to `main` is handled by the repository's existing CI/CD.

### H. PULL REQUEST RULES

IMPORTANT:

- Never push directly to the production branch; changes reach `main` only by merging the PR.
- Never overwrite existing articles.
- Never modify unrelated application code.
- Never create duplicate Pull Requests for the same article.
- If an existing PR already contains the same article, investigate and update it only when appropriate.

If GitHub access or permissions are unavailable, save the article as a draft and report the failure.

Do not claim that a Pull Request was created or merged unless GitHub confirms it.
